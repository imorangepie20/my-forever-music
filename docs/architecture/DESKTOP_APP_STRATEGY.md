# Desktop App Strategy

작성일: `2026-04-29`

## 결론

이 프로젝트는 먼저 웹앱을 완성하고, 이후 Windows 데스크탑 앱을 `Tauri 2` 셸로 확장하는 방향이 가장 적합합니다.

이유는 다음과 같습니다.

- 현재 프론트 템플릿이 이미 `React + Vite + TypeScript` 기반이라 재사용성이 높음
- Tauri는 기존 웹 프론트를 그대로 연결할 수 있음
- Windows 배포에 필요한 자동 업데이트, 자동 시작 같은 기능을 플러그인으로 확장 가능
- Electron보다 번들 크기와 메모리 부담을 줄이기 쉬움

## 권장 아키텍처

```text
apps/web
  -> 브라우저 사용자용 웹앱

apps/desktop
  -> Tauri 기반 Windows 데스크탑 셸
  -> 공통 UI/도메인 로직 재사용

packages/shared-types
  -> API DTO, 도메인 타입

packages/shared-utils
  -> 포맷터, 헬퍼, 클라이언트 공통 로직

packages/design-tokens
  -> 색상, 타이포, 간격, 테마 토큰

services/api
  -> Spring Boot 기반 인증, 사용자, 플레이리스트, 추천 오케스트레이션

services/ai
  -> 추천/AI 분석 서비스
```

## 지금부터 지켜야 할 설계 원칙

1. `apps/web` 안에 API 호출, 타입, 유틸을 과도하게 몰아넣지 말 것
2. 웹 전용 브라우저 API 사용은 얇은 어댑터 뒤로 숨길 것
3. 인증 상태, 사용자 설정, 플레이리스트 모델은 플랫폼 중립적으로 설계할 것
4. UI 컴포넌트는 데스크탑에서도 재사용 가능하게 입력/상태 의존성을 단순화할 것

## 웹과 데스크탑의 분리 기준

- 공통: 화면 컴포넌트
- 공통: 도메인 모델
- 공통: API 스키마와 검증
- 공통: 디자인 토큰
- 공통: 상태 관리 규칙
- 데스크탑 전용: 자동 시작
- 데스크탑 전용: 로컬 파일 접근
- 데스크탑 전용: 시스템 트레이
- 데스크탑 전용: 앱 업데이트
- 데스크탑 전용: OS 통합 기능

## Tauri를 우선 추천하는 이유

- 공식 문서 기준 `Tauri 2`는 기존 웹 프레임워크를 그대로 사용할 수 있음
- Windows 지원 전제에서 `WebView2`와 C++ Build Tools 요구사항이 명확함
- updater, autostart 같은 기능을 공식 플러그인으로 제공함

## Electron을 다시 검토해야 하는 경우

아래 요구가 강하면 그 시점에 Electron 또는 별도 네이티브 컴포넌트를 다시 검토합니다.

- 매우 무거운 백그라운드 프로세스 제어
- 복잡한 네이티브 드라이버/장치 통합
- Chromium 내장 런타임 고정이 꼭 필요한 경우
- 대규모 데스크탑 전용 생태계 의존이 필요한 경우

현재 단계에서는 그런 요구가 아직 확정되지 않았으므로, 기본 선택은 `Tauri 2`가 더 합리적입니다.

## 구현 순서

1. 웹앱 기능과 정보구조부터 확정
2. 공통 타입, 유틸, 디자인 토큰을 `packages/*`로 이동
3. API 계약을 `services/api` 중심으로 고정
4. 이후 `apps/desktop`에 Tauri 초기화
5. 마지막에 Windows 전용 기능만 추가
